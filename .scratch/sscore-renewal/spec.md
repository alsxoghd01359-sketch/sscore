# sscore 전체 개편 스펙

## Problem Statement

sscore는 축구 경기·순위·선수/팀 정보를 보여주는 앱이지만, 사용자 입장에서 다음 문제가 있다.

- 회원 기능이 구색만 있다. 비밀번호가 평문으로 저장되고, 로그인은 "성공"이라는 문자열만 돌려주며, 로그인 상태가 유지되지 않는다. 닉네임도 저장되지 않는다.
- 팔로우, 알림, 프로필, 탈퇴, 기기 간 동기화가 없어서 **회원**이 자기 관심 팀과 선수를 중심으로 앱을 쓸 수 없다.
- 누구나 호출할 수 있는 관리용·디버그용 주소가 열려 있어 데이터가 임의로 바뀌거나 외부 API 호출 한도를 소진당할 수 있다.
- 경기중계가 한정적이다. 라이브 스코어 자동 갱신은 꺼져 있고, 경기 상세 데이터는 요청마다 조합되며, 시즌이 코드에 고정돼 있다.
- 코드가 낡았다. 서비스 하나가 천 줄이 넘고 화면이 네트워크를 직접 호출한다. DB 구조는 자동 생성과 수동 SQL 파일이 어긋나 있다. 앱 서버 주소가 코드에 박혀 있고 평문 통신을 허용한다.

## Solution

기존 기능과 동작을 유지하면서 코드를 현대화하고, 구색만 있던 회원·개인화 기능을 실제로 동작하게 만든다.

- **게스트**는 로그인 없이 경기·순위·선수·팀·리그를 조회할 수 있다. 팔로우, 알림, 프로필 같은 개인화 기능을 누르면 로그인으로 안내한다.
- **회원**은 이메일과 비밀번호로 가입하고, 이메일로 받은 **인증코드**를 입력해 가입을 마친다. 로그인 상태는 유지되고, 닉네임·비밀번호·**응원 팀**을 관리하며, 탈퇴하면 30일의 **탈퇴 유예** 뒤 데이터가 삭제된다.
- 회원은 팀과 선수를 **팔로우**하고, 종류별·대상별로 **알림 설정**을 정해 경기 시작, 득점/이벤트, 경기 종료/결과, 라인업 발표 알림을 받는다. 프로필·팔로우·알림 설정은 **동기화**되어 다른 기기에서도 그대로 복원된다.
- 경기중계는 라이브 경기가 있을 때 약 15초 간격으로 갱신되고, 앱은 화면을 보는 동안 10~15초마다 새로 읽는다. 경기가 끝나면 확정 데이터가 저장되어 이후 조회가 빨라진다. **선수 평점**은 API-Football 값을 표시한다.
- 데이터센터(순위표, 선수·팀·리그 상세, 통합 검색)는 지금 기능을 유지하며 정리하고, 검색은 팀·선수·리그를 대상으로 한다.
- 화면 색은 라이트 테마와 주황 포인트로 이미 바뀌었다(이 스펙 이전에 완료).
- AI 승률 예측은 이 스펙에 포함하지 않고 가장 마지막 작업으로 미룬다.

회원 기반
1. As a 게스트, I want 로그인 없이 앱을 열어 경기를 볼 수 있기를, so that 가입 전에 앱이 쓸 만한지 확인할 수 있다

4. As a 신규 사용자, I want 입력한 이메일로 6자리 **인증코드**를 받기를, so that 내가 그 이메일의 주인임을 증명할 수 있다
5. As a 신규 사용자, I want 인증코드를 앱에서 입력해 가입을 완료하기를, so that 링크를 따로 열지 않아도 된다
6. As a 신규 사용자, I want 인증코드가 10분 뒤 만료되기를, so that 오래된 코드로 가입되지 않는다
7. As a 신규 사용자, I want 인증코드를 다시 받을 수 있기를, so that 메일을 놓쳐도 가입할 수 있다
8. As a 서비스 운영자, I want 재발송과 입력 실패 횟수를 제한하기를, so that 메일 남용과 코드 무작위 대입을 막을 수 있다

10. As a 신규 사용자, I want 인증을 마치지 않은 가입 시도는 회원이 되지 않기를, so that 확인되지 않은 이메일이 계정이 되지 않는다
11. As a 신규 사용자, I want 비밀번호가 8~20자이고 특수문자를 포함해야 한다는 규칙을 입력 중에 알려 주기를, so that 가입 실패를 반복하지 않는다
12. As a 신규 사용자, I want 닉네임이 2~12자이고 다른 회원과 겹치지 않는지 확인해 주기를, so that 나를 구분할 수 있는 이름을 쓸 수 있다

14. As a 회원, I want 로그인이 유지되어 앱을 다시 켜도 로그인 화면을 보지 않기를, so that 매번 입력하지 않아도 된다

16. As a 회원, I want 로그인 상태가 30분 단위 토큰과 14일짜리 갱신 토큰으로 관리되기를, so that 불편 없이 안전하게 쓸 수 있다

80. As a 사용자, I want 팀·선수·리그를 한 번에 검색하기를, so that 찾는 대상이 어떤 종류인지 몰라도 된다
81. As a 사용자, I want 검색 결과를 종류별로 구분해 보기를, so that 혼동하지 않는다
82. As a 사용자, I want 결과를 누르면 해당 상세 화면으로 가기를, so that 바로 이동한다
83. As a 사용자, I want 지원하는 리그가 빅5(EPL, 라리가, 분데스리가, 세리에A, 리그1)이기를, so that 범위가 명확하다

운영과 보안
84. As a 서비스 운영자, I want 데이터 적재·갱신·취소 같은 관리 기능이 ADMIN 권한 회원만 호출할 수 있기를, so that 외부인이 데이터를 바꾸거나 호출 한도를 소진시키지 못한다
85. As a 서비스 운영자, I want 디버그용 주소가 사라지기를, so that 외부 API 원본 응답이 노출되지 않는다
86. As a 서비스 운영자, I want 상태를 바꾸는 관리 기능이 조회 요청이 아닌 변경 요청이기를, so that 링크 하나로 실행되지 않는다
87. As a 개발자, I want DB 구조 변경이 번호가 붙은 마이그레이션 파일로 관리되기를, so that 어느 PC에서든 같은 구조가 만들어진다
88. As a 개발자, I want 기존 DB 데이터가 마이그레이션 도입 후에도 보존되기를, so that 적재한 데이터를 잃지 않는다
89. As a 개발자, I want API 키와 DB 비밀번호가 환경 파일에만 있기를, so that 저장소에 비밀값이 올라가지 않는다
90. As a 개발자, I want 앱의 서버 주소가 빌드 종류별로 분리되기를, so that 에뮬레이터와 실기기에서 모두 개발할 수 있다
91. As a 개발자, I want 화면이 서버를 직접 호출하지 않고 데이터 계층을 거치기를, so that 로그인 토큰·에러·로딩을 한 곳에서 처리한다
92. As a 사용자, I want 네트워크 오류가 났을 때 오류 안내와 재시도를 받기를, so that 빈 화면에서 멈추지 않는다
93. As a 사용자, I want 로그인 만료나 서버 오류가 일관된 메시지로 보이기를, so that 무슨 일인지 이해한다

## Implementation Decisions

인증과 회원
- 인증은 이메일+비밀번호이고 로그인 상태는 JWT로 관리한다. 액세스 토큰 30분, 갱신 토큰 14일. 앱은 토큰을 암호화 저장소에 보관한다.
- 비밀번호는 BCrypt로 해시한다. 규칙은 기존과 같이 8~20자에 특수문자 포함.
- 이메일 인증은 6자리 인증코드 방식이다. 유효시간 10분, 재발송 횟수와 입력 실패 횟수를 제한한다. 같은 방식을 비밀번호 재설정에도 쓴다. 인증을 마치기 전에는 회원으로 취급하지 않는다.
- 메일은 SMTP로 보낸다. 개발 단계에서는 개인 메일 계정의 앱 비밀번호를 환경 파일로 주입한다.
- 닉네임은 2~12자(한글·영문·숫자, 공백·특수문자 불가)이고 중복을 허용하지 않는다. 중복 검사는 DB 유일성 제약으로도 보장한다.
- 회원은 역할(일반/ADMIN)을 가진다. 비밀번호 변경과 탈퇴는 이미 발급된 모든 토큰을 무효화한다.
- 로그인 실패 응답은 이메일과 비밀번호 중 어느 쪽이 틀렸는지 구분하지 않는다.
- 로그인·가입 응답은 문자열이 아니라 구조화된 응답과 적절한 상태 코드를 쓴다. 앱도 문자열 비교를 버린다.
- 기존 users 테이블에는 데이터가 없으므로 구조를 자유롭게 바꿔도 된다. 닉네임, 역할, 인증 상태, 탈퇴 요청 시각을 갖는다.

탈퇴
- 탈퇴 요청 시 회원은 즉시 탈퇴 유예 상태가 되어 로그인이 막히고 토큰이 무효화되며 알림이 중단된다. 유예 30일 안에 복구 가능하고, 이후 스케줄러가 회원과 그에 딸린 팔로우·알림 설정을 영구 삭제한다.
- 유예 중 이메일로 가입하려 하면 복구 안내를 한다. 삭제 후에는 같은 이메일로 새로 가입할 수 있다.

팔로우·알림
- 팔로우 대상은 팀과 선수다. 응원 팀은 회원당 하나이고, 지정하면 팔로우가 자동으로 생긴다. 응원 팀을 바꿔도 이전 팀의 팔로우는 남는다.
- 알림 설정은 전역 종류별 켜짐/꺼짐과 팔로우 대상별 켜짐/꺼짐의 조합이며 서버에 저장되어 동기화된다. 알림이 나가려면 종류와 대상이 모두 켜져 있어야 한다.
- 알림 종류는 경기 시작, 득점/이벤트, 경기 종료/결과, 라인업 발표.
- 푸시는 FCM으로 보낸다. 회원은 기기 토큰을 서버에 등록하며, 로그아웃·탈퇴 시 해당 기기 토큰은 해제된다. 같은 이벤트는 한 회원에게 한 번만 보낸다.
- 알림 발생은 라이브 갱신 스케줄러가 경기 상태 변화(시작, 득점·이벤트, 종료, 라인업 확정)를 감지할 때 만든다. 이미 보낸 이벤트는 다시 보내지 않도록 기록한다.
- 알림 본문에서 해당 경기 상세로 이동할 수 있어야 한다.

경기중계
- 서버 스케줄러는 라이브 경기가 있을 때만 약 15초 간격으로 외부 API를 호출한다. 호출은 리그별이 아니라 진행 중 경기 전체를 한 번에 가져오는 방식으로 한도 안에서 운영한다(Pro, 하루 7,500회).
- 앱은 화면이 보이는 동안만 10~15초 간격으로 서버를 다시 읽는다. 서버가 변경을 밀어 주는 방식(스트리밍)은 쓰지 않는다.
- 경기 상세(타임라인, 라인업, 통계, 선수 평점)는 진행 중에는 짧게 캐시하고, 경기가 끝나면 확정본을 DB에 저장한 뒤 이후에는 DB에서만 제공한다.
- 선수 평점은 외부 API가 주는 값을 그대로 쓴다. 사용자 투표는 없다.
- 시즌은 현재 날짜로 자동 결정한다. 지원 리그는 빅5이며, 리그 목록은 설정으로 확장할 수 있는 구조로 만든다.
- 외부 API 호출과 응답 해석을 한 모듈로 모으고, 알 수 없는 응답 형태가 와도 서버가 조용히 잘못된 데이터를 저장하지 않게 한다.

데이터센터
- 순위표, 선수·팀·리그 상세는 현재 제공되는 정보를 유지한다. 앱과 서버 사이의 요청 경로와 응답 형태는 가능한 한 하위 호환을 지키며, 바꿔야 하면 앱과 서버를 함께 바꾼다.
- 통합 검색은 팀·선수·리그를 대상으로 하고, 결과에 종류를 표시한다.
- 외부 데이터 적재(대량 초기 적재, 이벤트·선수 통계 적재, 우승 이력 등)는 관리 기능으로 남기되 ADMIN만 호출한다. 디버그용 원본 응답 주소는 제거한다.

저장소와 스키마
- DB 구조는 Flyway 마이그레이션으로 관리한다. 현재 DB 구조를 첫 기준선으로 잡고 기존 데이터를 보존한다. 이후 변경은 번호가 이어지는 파일로 추가한다. JPA 자동 생성 모드는 검증 전용으로 바꾼다.
- 기존 수동 SQL 스키마 파일과 엔티티 사이의 불일치(FK, 유일성, 비어 있을 수 없는 값)를 기준선에서 정리한다.
- 날짜·시간은 문자열이 아닌 시각 타입으로 저장하도록 정리한다(데이터 이전 포함).

서버 구조
- 거대한 조회 서비스와 외부 API 서비스를 책임별로 나눈다(인증, 회원, 팔로우, 알림, 라이브 갱신, 경기 상세, 순위, 선수, 팀, 리그, 검색). 컨트롤러는 외부 API 호출이나 비밀값을 직접 다루지 않는다.
- 오류는 공통 방식으로 상태 코드와 메시지를 돌려준다. 예외를 삼키거나 콘솔에만 찍지 않는다.
- 파일명과 클래스명의 불일치, 잘못된 위치에 있는 클래스를 정리한다.
- 코드를 계층별(컨트롤러/서비스/엔티티 폴더)이 아니라 기능별로 묶는다. 서버는 인증, 회원, 팔로우, 알림, 경기, 리그, 팀, 선수, 검색, 관리자, 공통(외부 API·오류 처리)으로, 앱도 같은 기능 단위 폴더로 나눈다. 정리는 각 티켓이 맡은 기능의 코드를 작업하면서 함께 하고, 이동만 하는 일괄 작업은 만들지 않는다.

안드로이드
- 언어와 XML 뷰 구조는 유지하고 Compose로 바꾸지 않는다. ViewModel+Repository+Coroutines 구조로 점진적으로 옮기며, 화면은 해당 기능을 작업할 때 함께 옮긴다.
- 서버 주소는 빌드 종류별로 분리하고, 평문 통신 허용은 개발 빌드에만 둔다.
- 앱 시작 시 저장된 로그인 상태가 있으면 바로 메인으로 가고, 없으면 게스트로 메인에 들어간다. 개인화 기능은 로그인 여부를 확인해 로그인 화면으로 안내한다.
- 템플릿에서 남은 앱 이름·테마 이름·사용하지 않는 설정과 중복 의존성을 정리한다.

작업 순서
- 회원 기반 → 데이터센터 → 경기중계 → 개인화 → (이 스펙 밖) AI 승률 예측.

사전 준비(사용자가 제공)
- 이메일 발송용 SMTP 계정, FCM용 Firebase 프로젝트와 서비스 계정 키(개인화 단계 시작 전).

## Testing Decisions

- 좋은 테스트는 내부 구현이 아니라 외부에서 보이는 동작만 확인한다. 즉 HTTP 요청을 보내고, 응답과 그 뒤 DB 상태, 그리고 외부로 나간 메일·푸시를 검증한다.
- 테스트 경계는 **백엔드 REST API 하나**다. 기능별 테스트는 모두 이 경계로 작성하며 별도의 내부 경계를 새로 만들지 않는다. 안드로이드는 이번 스펙에서 자동 테스트 경계를 만들지 않는다.
- 외부 의존 세 곳은 가짜로 대체한다: 외부 축구 API(경기·이벤트 시나리오를 재생), 메일 발송(받은 인증코드를 확인), 푸시 발송(나간 알림 확인). 시간은 주입 가능한 시계로 대체해 만료와 유예를 검증한다.
- DB는 Testcontainers로 실제 MySQL 8을 띄워 사용한다. 마이그레이션, 유일성·FK 제약, 전문 검색이 실제와 같이 동작함을 검증한다. 이를 위해 개발 PC에서 Docker가 실행 중이어야 한다.
- 우선 검증할 동작
  - 가입(인증코드 발급·만료·재발송·실패 제한·중복 이메일·닉네임 규칙), 로그인, 토큰 갱신, 로그아웃, 비밀번호 변경·재설정 후 토큰 무효화
  - 탈퇴 유예(즉시 차단, 30일 안 복구, 30일 뒤 삭제, 유예 중 알림 중단)
  - 응원 팀 지정 시 자동 팔로우, 팔로우 추가·해제, 알림 설정 저장과 다른 기기에서의 복원
  - 알림 대상 선정(종류·대상 설정 조합, 중복 방지, 양 팀 팔로우 시 1회)
  - 라이브 갱신이 경기 상태 변화를 감지해 알림을 만들고, 라이브 경기가 없으면 외부 호출을 하지 않는지
  - 종료 경기 확정본 저장 후 외부 호출 없이 상세가 제공되는지
  - 검색(팀·선수·리그), 권한(게스트 조회 허용, 개인화·관리 기능 거부, ADMIN만 관리 기능 허용)
- 선행 테스트 사례(prior art): 현재 저장소에는 템플릿이 만든 컨텍스트 로딩 테스트 하나뿐이라 참고할 기존 사례가 없다. 첫 테스트가 이후 테스트의 기준 틀이 되도록 만든다.

## Out of Scope

- AI 승률 예측(3.6). 사용할 데이터와 방식을 정한 뒤 별도 스펙으로 다룬다.
- 사용자 투표 방식의 선수 평점.
- 소셜 로그인, 프로필 사진 업로드.
- 리그 확대(챔피언스리그, K리그 등)와 경기·리그 단위 팔로우.
- 알림 방해금지 시간대.
- 서버 푸시 스트리밍(SSE/WebSocket), 클라우드 배포·HTTPS·운영 도메인.
- Jetpack Compose로의 화면 전환, 안드로이드 UI 자동 테스트.
- 색상·테마 변경(이미 완료).

## Further Notes

- 용어는 프로젝트 용어집의 **회원, 게스트, 인증코드, 응원 팀, 팔로우, 알림 설정, 동기화, 탈퇴 유예, 선수 평점**을 따른다.
